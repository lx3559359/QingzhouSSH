# QingzhouSSH Milestone 3：可视化工作流与恢复设计

## 1. 目标

Milestone 3 在已经通过真实 SSH/SFTP 验证的 M2 服务之上增加工作流，不复制第二套命令、日志或传输实现。用户可以在无 SSH 终端的前提下编辑、校验和运行单服务器工作流，并在失败、取消、崩溃或部署覆盖后得到准确、可解释、可恢复的状态。

完成门槛是：参考部署工作流能够成功运行，也能够在每类可执行节点失败时停在准确节点；失败节点可重试，应用中断会标记远端状态未确认，覆盖文件创建的恢复点可经二次确认回滚。

## 2. 首版范围与非目标

节点类型：

- 开始；
- 执行内置快捷任务；
- 执行受控单条命令或多行脚本；
- SFTP 上传文件；
- SFTP 下载文件；
- 检索普通或 gzip 日志；
- 条件判断；
- 停止并提示。

首版只允许一台服务器、一个当前节点和有向无环图。没有循环、并行、多服务器批量、人工审批、任意 JavaScript 表达式或交互式终端。失败不会自动沿图继续，避免扩大影响。

## 3. 持久化模型

新增 `0003_workflows.sql`：

- `workflows`：稳定标识、名称、描述、当前版本、创建/更新时间；
- `workflow_versions`：不可变版本、规范化定义 JSON、SHA-256、创建时间；
- `workflow_runs`：工作流/版本/服务器、状态、当前节点、创建/开始/结束时间、错误分类、是否可重试；
- `workflow_node_runs`：节点、尝试次数、状态、关联 M2 execution ID、时间、退出码、结果摘要和错误；
- `workflow_restore_points`：运行/节点、远端路径、本地数据根相对路径、SHA-256、大小、状态、适用条件和时间；
- `workflow_run_events`：单调序号、类型、脱敏 JSON 载荷和时间，用于重载恢复时间线。

工作流定义以强类型 Rust DTO 解析后再保存。编辑保存会创建新版本，旧运行永远引用旧版本；数据库不保存凭据或脚本文本以外的秘密。脚本文本属于用户工作流定义，确认弹窗只显示长度/行数/摘要，不回显全文。

## 4. 图与节点契约

`WorkflowDefinition` 包含 `id`、`name`、`description`、`version`、节点和边。节点有稳定 UUID、显示名称、画布坐标和带判别字段的配置。边包含来源、目标和分支：普通节点使用 `success`，条件节点必须各有一条 `true` 与 `false`。

保存和运行前都执行相同的 Rust 校验：

- 恰好一个开始节点，开始节点无入边且恰好一条出边；
- 停止节点无出边；普通可执行节点最多一条 `success` 出边；条件节点恰好有 `true`/`false` 两条不同分支；
- 所有边引用现存节点，无自环、无重复边、无有向环；
- 所有节点从开始节点可达，且工作流至少有一个终止路径；
- 节点参数通过 M2 的任务、日志和传输校验器；目标系统兼容性在运行前针对所选服务器再次检查；
- 自定义命令/脚本仍要求非交互、超时和危险确认；
- 工作流最多 100 个节点、200 条边，条件文本最长 512 字节。

条件只允许读取已经完成的来源节点：

- `exit_code` 与整数比较；
- 结构化结果中的受限点路径与字符串/数字/布尔值比较；
- 脱敏输出摘要的固定文本包含或不包含。

不接受正则、shell、脚本或动态属性访问。

## 5. 运行状态机

工作流状态：`queued`、`running`、`paused`、`succeeded`、`cancelled`、`uncertain`、`rolled_back`、`rollback_failed`。

节点状态：`pending`、`running`、`succeeded`、`failed`、`cancelled`、`uncertain`、`skipped`。

执行器严格串行：选取当前节点，持久化 `running`，调用现有 M2 服务，持久化关联 execution 与终态，再计算唯一后继。条件分支确定后，另一分支中不可到达的节点标记 `skipped`。到达正常终点时工作流成功；到达“停止并提示”时以 `paused` 结束并保存提示。

任何可执行节点失败时工作流进入 `paused`，不会运行后续节点。用户可以仅重试失败节点；重试创建新的节点 attempt 和新的 M2 execution，成功后从该节点继续。不可重试错误会给出原因，但仍保留诊断和恢复点。

取消通过运行注册表传递到当前 M2 execution。确认远端已停止则节点/工作流为 `cancelled`；无法确认时均为 `uncertain`。启动恢复把遗留 `running` 工作流和节点改为 `uncertain`，不自动续跑。

## 6. 恢复点与回滚

上传节点启用“覆盖前创建恢复点”时，在上传前通过同一受信 SSH/SFTP 会话把原远端文件流式下载到：

`<data-root>/backups/workflows/<run-id>/<node-id>/<safe-name>`

恢复点记录远端绝对路径、大小、SHA-256、原文件是否存在、创建时间和工作流/服务器适用条件。若原文件不存在，则恢复语义是回滚时删除本次新建文件；该删除动作同样需要确认。

回滚按成功变更的逆序执行。开始前展示服务器、远端路径和动作摘要，并要求 `dangerousConfirmed=true`。恢复已有文件时先上传到远端临时文件、校验 SHA-256 再原子替换；任一步无法确认时状态为 `rollback_failed`，不得显示成功。

用户可在终态运行后清理恢复点。清理只接受数据库登记且位于 `backups/workflows` 下的相对路径，删除后记录为 `expired`；运行中的恢复点不能清理。

## 7. 事件、诊断与脱敏

`WorkflowEvent` 使用单调序号，包含运行状态、节点状态、条件结果、子执行事件摘要、恢复点状态和完成事件。事件与数据库载荷统一经过 Redactor；单事件和总输出继续使用 M2 上限。

诊断包由 Rust 在 `downloads` 下生成脱敏 JSON，包含工作流版本校验和、运行/节点时间线、错误分类、M2 execution 引用、恢复点元数据和系统能力摘要，不包含凭据、私钥、完整敏感参数或任意本地绝对路径。

## 8. Tauri API

新增命令：

- `list_workflows`、`get_workflow`、`save_workflow`、`delete_workflow`；
- `validate_workflow`；
- `start_workflow_run`、`cancel_workflow_run`、`retry_workflow_node`；
- `list_workflow_runs`、`get_workflow_run`；
- `rollback_workflow_run`、`cleanup_workflow_restore_points`；
- `export_workflow_diagnostics`。

所有命令使用 camelCase TypeScript 参数与 Rust `rename_all = "camelCase"` DTO。前端只拿相对文件路径，不持有 SSH/SFTP 会话或本地恢复点绝对路径。

## 9. 界面

工作流页替换 M2 说明页：

- 左侧白银渐变步骤库与工作流列表；
- 中间点阵画布、立体节点卡片、SVG 连线和缩放；
- 右侧悬浮参数/连接/条件面板，底部继续露出画布背景；
- 顶部保存、校验和运行；运行前展示完整诊断及危险动作摘要；
- 运行态显示节点时间线、当前节点、失败原因、重试、停止、回滚和诊断下载。

节点可点击添加和拖动定位。连接通过右侧明确的“下一步/真分支/假分支”选择器编辑，避免首版实现难以无障碍测试的自由拉线。卡片继续使用已批准的白银渐变、边缘高光和强三层阴影，保证正文对比度。

## 10. 测试与验收

- 迁移、不可变版本、图校验、条件求值、状态转换、崩溃恢复和事件序号单元/集成测试；
- 节点适配测试证明工作流复用 M2 服务并留下关联 execution；

- React 编辑器、连接面板、校验诊断、危险确认、运行时间线、失败重试和回滚测试；
- AsyncSSH 真实夹具参考部署闭环，并对每类可执行节点注入失败，验证准确暂停、重试和恢复；
- 凭据/脚本敏感 canary、项目内路径、C 盘与 D 盘根目录污染扫描；
- 前端构建、Rust fmt/Clippy/全量测试和 Tauri 调试构建全部通过。

## 11. M4 边界

本里程碑不实现安装包、签名、更新清单、GitHub Releases 或 ModelScope 同步。M3 只为 M4 提供稳定数据库迁移、诊断文件和可执行产物输入，不显示伪在线更新状态。
